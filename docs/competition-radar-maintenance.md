# 赛事雷达维护手册

赛事雷达是人工策展的发现与决策辅助，不是赛事主办方数据库，也不承诺实时更新。任何日期、资格、奖金和规则在对外表述前，都应回到主办方最新页面核对。

## 维护闭环

每次更新按以下顺序完成：

1. **发现**：从官方站、赛事平台、政府公告、主办方社交账号或可信媒体发现候选赛事。
2. **证据**：保存能够支持赛事存在、报名／提交截止、资格、奖励和行动链接的公开来源。聚合站可用于发现，但不能单独支撑高信用结论。
3. **人工复核**：区分报名截止、作品提交、活动举行和结果公布；确认时间、时区、地域限制、团队人数、费用及奖金条件。无法确认的内容明确写“待确认”“预计”或“参考”，不能补造精确日期。
4. **校验**：运行数据校验、构建和链接审计，查看数量、状态桶、详情页、JSON 输出及安全负例。
5. **部署**：只部署已经人工复核并通过构建的改动；上线后抽查雷达、一个详情页、JSON 和外部行动链接。

## 人工复核队列

先生成按风险排序的人工复核队列。它会把即将截止但未核验、死链／不确定链接、估算日期、已过期日期、陈旧核验和缺少一手来源的记录排到前面：

```bash
npm run radar:review -- --today 2026-07-30 --limit 30
```

在自动化或维护提醒中，可用 JSON 输出并让 critical 项触发非零退出码：

```bash
npm run radar:review -- --json --fail-on-critical
```

`--today` 只用于可复现审计，日常运行可省略。队列是“优先人工检查什么”，不是自动删除或自动改写依据。

## 数据编辑原则

- `id` 发布后保持稳定，它同时用于详情路由、URL hash 和 JSON feed。
- `deadlineISO` 当前是兼容字段。它应对应用户当前最需要行动的截止节点，不能用活动日期冒充。
- `timeline` 应明确写出“报名截止”“提交截止”“活动开始”等节点，避免只写“截止”。
- `url` 是主要行动入口，但不一定等于独立证据；尽量补充 `sources`。
- `sources[].date` 暂时保留现有语义。新增来源时，在标题或上下文中说明它是公告发布日期还是核验日期，避免混淆。
- 奖励中的投资额度、Credits、补贴、采购机会和现金奖必须分别描述；有落地、注册或孵化条件时必须写出条件。
- 预计日期、参考上届和滚动项目不得被描述为官方确定日期。

## 构建与路由验收

```bash
npm run build
```

构建后至少检查：

- `dist/competitions/index.html` 存在；
- 每个现有赛事 ID 都有一个 `dist/competitions/<id>/index.html`；
- 未知 ID 没有生成静态页面，因此由静态托管自然返回 404；
- `dist/competitions.json` 是合法 JSON，`count` 等于数据记录数；
- `dist/llms.txt` 保持纯文本；
- 详情页只有在时间轴明确给出活动开始节点时，Event JSON-LD 才包含 `startDate`；
- 报名截止和提交截止不能被写成 Event `startDate`。

建议额外抽查：

```bash
node -e "const fs=require('node:fs');const d=JSON.parse(fs.readFileSync('dist/competitions.json','utf8'));console.log(d.count,d.items[0].id)"
find dist/competitions -mindepth 2 -name index.html | wc -l
```

## 只读链接审计

审计脚本只发出有界 GET 请求，不会登录、报名、修改远端数据或写回赛事数据。

先做目标策略与 DNS 安全检查：

```bash
npm run radar:links -- --dry-run --limit 5
```

再对少量记录发起真实检查：

```bash
npm run radar:links -- --id amddevmaster2026 --limit 3
```

完整审计：

```bash
npm run radar:links
```

需要把确定的 404／410 作为命令失败时：

```bash
npm run radar:links -- --fail-on-dead
```

安全边界：

- 只允许 `http:` 和 `https:`；
- 拒绝 URL 内嵌账号密码；
- 拒绝 localhost、单标签内网主机、常见内网后缀、私网／保留 IP 和解析到这些地址的域名；
- 拒绝非 80／443 端口；
- 每次重定向重新验证目标，且限制跳数；
- 使用 Node 默认 TLS 证书验证；检测到 `NODE_TLS_REJECT_UNAUTHORIZED=0` 时拒绝运行；
- 使用 GET，不用 HEAD 代替真实可访问性检查；
- 每次请求限制时间和读取的响应体大小。

状态含义：

- `ok`：最终响应为 2xx；
- `bot_blocked`：401、403、407、429，或响应明显是验证码／机器人防护；这不代表赛事关闭；
- `dead`：明确的 404、410，或 DNS 确认不存在；
- `uncertain`：超时、5xx、重定向异常、TLS／网络问题或其他无法确定的结果。

退出码约定：

- `0`：审计存在可达证据，且没有触发指定失败条件；
- `1`：启用 `--fail-on-dead` 后发现明确死链；
- `2`：参数、数据选择、TLS 配置或不安全目标错误；
- `3`：至少一半结果不确定，或没有任何 `ok`／`bot_blocked`，视为系统性检查失败。

## 连续性与人工复核

自动审计结果不能直接改赛事状态：

- 一次 `ok` 可以清除该链接先前的失败观察。
- `bot_blocked` 不累计为死链；应使用普通浏览器人工打开。
- `uncertain` 不触发删除、过期或降级；下一次维护窗口重试。
- `dead` 至少需要 **两次连续审计**，两次间隔至少 24 小时，并由人工浏览器再次确认后，才能修改或移除链接。
- 如果失败集中发生在同一次运行、同一网络、同一域名或多数站点，应视为系统性失败，不得批量更改数据。
- 审计输出应作为 CI／维护记录保留，以便比较连续结果；脚本本身保持只读，不维护隐式状态。

## 每日安全监控

本机 LaunchAgent `com.siuser.competition-monitor` 每天 08:30 运行：

```bash
npm run radar:monitor
```

它会把人工复核队列、全量有界链接审计、与上次相比的新增死链／恢复项写入：

```text
~/.competition-monitor/radar-report.json
```

本地手动验证可使用：

```bash
npm run radar:monitor -- --dry-run --today 2026-07-30 --no-notify
```

监控不会编辑赛事数据、自动发布、登录、提交表单或绕过 TLS。只有“新确认死链”或“死链恢复”时才发送 macOS 通知；日期、资格、奖励和规则仍必须由人工查看一手来源后再改数据。仓库内旧的 `competition-monitor.py` 仅作为历史实现保留，不再由 LaunchAgent 调用；它覆盖不足且不满足当前 TLS 安全要求，不应重新启用。

## JSON 与公开边界

`/competitions.json` 仅公开赛事发现需要的固定字段：

- 身份、名称、组织、分类、等级和适配分；
- 地点、日期标签、兼容截止日期；
- 简介、适用人群、有限数量的奖励与时间轴；
- 详情链接、行动链接和有限数量的来源。

它不输出内部维护备注、抓取日志、隐藏评分依据、环境信息或凭据。新增字段前先判断它是否是用户完成赛事发现和核验所必需的公开信息。

## 部署后抽查

1. 打开 `/competitions/`，验证搜索、筛选和详情选择。
2. 打开一个 `/competitions/<id>/`，核对唯一 H1、canonical、来源和外部行动链接。
3. 请求 `/competitions.json`，确认 Content-Type、记录数和字段边界。
4. 请求 `/llms.txt`，确认没有 HTML 包装。
5. 对本次新增或改动的外部链接用浏览器人工确认。

若页面构建成功但官方规则仍有歧义，保持保守描述并标记待确认，不以部署完成替代事实核验。
