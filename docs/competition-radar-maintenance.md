# 赛事雷达维护手册

赛事雷达是人工策展的发现与决策辅助，不是赛事主办方数据库，也不承诺实时更新。任何日期、资格、奖金和规则在对外表述前，都应回到主办方最新页面核对。

## 维护闭环

每次更新按以下顺序完成：

1. **发现**：从官方站、赛事平台、政府公告、主办方社交账号或可信媒体发现候选赛事。
2. **证据**：保存能够支持赛事存在、报名／提交截止、资格、奖励和行动链接的公开来源。聚合站可用于发现，但不能单独支撑高信用结论。
3. **人工复核**：区分报名截止、作品提交、活动举行和结果公布；确认时间、时区、地域限制、团队人数、费用及奖金条件。无法确认的内容明确写“待确认”“预计”或“参考”，不能补造精确日期。
4. **校验**：运行数据校验、构建和链接审计，查看数量、状态桶、详情页、JSON 输出及安全负例。
5. **部署**：只部署已经人工复核并通过构建的改动；上线后抽查雷达、一个详情页、JSON 和外部行动链接。

## 人工复核队列

先生成按风险排序的人工复核队列。它会把即将截止但未核验、死链／不确定链接、估算日期、已过期日期、陈旧核验和缺少一手来源的记录排到前面：

```bash
npm run radar:review -- --today 2026-07-30 --limit 30
```

在自动化或维护提醒中，可用 JSON 输出并让 critical 项触发非零退出码：

```bash
npm run radar:review -- --json --fail-on-critical
```

`--today` 只用于可复现审计，日常运行可省略。队列是“优先人工检查什么”，不是自动删除或自动改写依据。

## 数据编辑原则

- 新候选优先收录 AI 软件、Agent、算法、创业和轻硬件机会。**纯视频或纯音乐赛事默认不再新增，也不进入主动推荐。**只有官方证据明确表明奖励相对好拿（例如有效参与即有固定奖励、奖励覆盖率高、低门槛多名额），才可用 `curation.rewardAccessibility: "high"` 和非空 `curation.rewardEvidence` 作为例外；总奖池大或冠军奖金高本身不构成例外。
- 混合赛事若主要交付物是可运行软件 / Agent，仅有一个可选音乐或视频子赛道，不视为纯视频 / 音乐赛事；在 `curation.primaryFormats` 写主要交付类型，在 `secondaryFormats` 写可选方向。
- `id` 发布后保持稳定，它同时用于详情路由、URL hash 和 JSON feed。
- `deadlineISO` 当前是兼容字段。它应对应用户当前最需要行动的截止节点，不能用活动日期冒充。
- `timeline` 应明确写出“报名截止”“提交截止”“活动开始”等节点，避免只写“截止”。
- `url` 是主要行动入口，但不一定等于独立证据；尽量补充 `sources`。
- `sources[].date` 暂时保留现有语义。新增来源时，在标题或上下文中说明它是公告发布日期还是核验日期，避免混淆。
- 奖励中的投资额度、Credits、补贴、采购机会和现金奖必须分别描述；有落地、注册或孵化条件时必须写出条件。
- 预计日期、参考上届和滚动项目不得被描述为官方确定日期。

## 大厂官网覆盖与官方原始目录

全量检查结果分为两层，不能互相替代：

- `src/data/competition-official-coverage.js` 是官网入口覆盖台账。当前边界为国内大厂／官方开发者入口 24 个、国际大厂 20 个、官方赛事平台 8 个，共 52 个入口；每条记录包含官网 URL、检查日期、覆盖状态、关联的站内赛事 ID 和检查说明。
- `src/data/competition-official-catalogs.js` 及其关联 JSON 是官方原始目录快照。它保留官网返回的全部赛事，不因截止、资格、内部限定、校内限定或测试赛而丢弃；赛事雷达中的精选记录仍按可行动性和策展规则独立维护。

2026-08-06 的目录基线为：腾讯云 11／11、华为云 423／423、火山杯 63／63。火山杯目录含 62 个独立赛和 1 个测试子赛；其中 36 条作品提交截止不早于检查日，20 条在检查日处于提交窗口，16 条尚未开始提交。华为目录含 5 条当前进行中记录和 418 条历史／已结束记录。

杭州云谷中心与魔搭社区必须作为独立入口检查。魔搭 `/active` 是动态 SPA，竞赛目录另有官方 `/api/v1/competitions` 接口。2026-08-09 增量检查时，接口元数据报告 `TotalCount: 117`，但分页只能取得 112 条唯一记录，第 15 页重复第 14 页；因此覆盖状态保持 `partial`，不能声称已抓齐 117／117，也不能据此断言当前只有已收录项目。入口边界或官方目录发生变化时，应同时更新对应测试，确认官网台账没有漏项，原始目录也没有被策展过滤。

同次增量检查从魔搭当前目录新增 5 项可行动机会：AI+∞ 开发者创作大赛、MiniCPM × 昇腾挑战赛、Production AI Skills 大赛、VentureD Vibe Coding 黑客松和硅碳 AI 诊疗挑战赛。外滩黑客松的 Qoder 页面与站内既有 `bund` 是同一赛事，只补来源不重复建档。华为终端开发者入口另新增两项激励计划，并以 `recordType: "program"` 明确区别于传统竞赛。

官方接口可能随时调整，不把接口响应数量永久当作平台总量。刷新目录时应保存检查日期、请求边界和返回总量，分页拉全后再核对首尾记录与去重结果；如果只能获得首屏、页面依赖登录或动态渲染，应明确标为 `partial`，不得写成全量。

## 构建与路由验收

```bash
npm run build
```

构建后至少检查：

- `dist/competitions/index.html` 存在；
- 每个现有赛事 ID 都有一个 `dist/competitions/<id>/index.html`；
- 未知 ID 没有生成静态页面，因此由静态托管自然返回 404；
- `dist/competitions.json` 是合法 JSON，`count` 等于数据记录数；
- `dist/llms.txt` 保持纯文本；
- 详情页只有在时间轴明确给出活动开始节点时，Event JSON-LD 才包含 `startDate`；
- 报名截止和提交截止不能被写成 Event `startDate`。

建议额外抽查：

```bash
node -e "const fs=require('node:fs');const d=JSON.parse(fs.readFileSync('dist/competitions.json','utf8'));console.log(d.count,d.items[0].id)"
find dist/competitions -mindepth 2 -name index.html | wc -l
```

## 只读链接审计

审计脚本只发出有界 GET 请求，不会登录、报名、修改远端数据或写回赛事数据。

先做目标策略与 DNS 安全检查：

```bash
npm run radar:links -- --dry-run --limit 5
```

再对少量记录发起真实检查：

```bash
npm run radar:links -- --id amddevmaster2026 --limit 3
```

完整审计：

```bash
npm run radar:links
```

需要把确定的 404／410 作为命令失败时：

```bash
npm run radar:links -- --fail-on-dead
```

安全边界：

- 只允许 `http:` 和 `https:`；
- 拒绝 URL 内嵌账号密码；
- 拒绝 localhost、单标签内网主机、常见内网后缀、私网／保留 IP 和解析到这些地址的域名；
- 拒绝非 80／443 端口；
- 每次重定向重新验证目标，且限制跳数；
- 使用 Node 默认 TLS 证书验证；检测到 `NODE_TLS_REJECT_UNAUTHORIZED=0` 时拒绝运行；
- 使用 GET，不用 HEAD 代替真实可访问性检查；
- 每次请求限制时间和读取的响应体大小。

状态含义：

- `ok`：最终响应为 2xx；
- `bot_blocked`：401、403、407、429，或响应明显是验证码／机器人防护；这不代表赛事关闭；
- `dead`：明确的 404、410，或 DNS 确认不存在；
- `uncertain`：超时、5xx、重定向异常、TLS／网络问题或其他无法确定的结果。

退出码约定：

- `0`：审计存在可达证据，且没有触发指定失败条件；
- `1`：启用 `--fail-on-dead` 后发现明确死链；
- `2`：参数、数据选择、TLS 配置或不安全目标错误；
- `3`：至少一半结果不确定，或没有任何 `ok`／`bot_blocked`，视为系统性检查失败。

## 连续性与人工复核

自动审计结果不能直接改赛事状态：

- 一次 `ok` 可以清除该链接先前的失败观察。
- `bot_blocked` 不累计为死链；应使用普通浏览器人工打开。
- `uncertain` 不触发删除、过期或降级；下一次维护窗口重试。
- `dead` 至少需要 **两次连续审计**，两次间隔至少 24 小时，并由人工浏览器再次确认后，才能修改或移除链接。
- 如果失败集中发生在同一次运行、同一网络、同一域名或多数站点，应视为系统性失败，不得批量更改数据。
- 审计输出应作为 CI／维护记录保留，以便比较连续结果；脚本本身保持只读，不维护隐式状态。

## 每日安全监控

本机 LaunchAgent `com.siuser.competition-monitor` 每天 08:30 运行：

```bash
npm run radar:monitor
```

它会把人工复核队列、全量有界链接审计、与上次相比的新增死链／恢复项写入：

```text
~/.competition-monitor/radar-report.json
```

本地手动验证可使用：

```bash
npm run radar:monitor -- --dry-run --today 2026-07-30 --no-notify
```

监控不会编辑赛事数据、自动发布、登录、提交表单或绕过 TLS。只有“新确认死链”或“死链恢复”时才发送 macOS 通知；日期、资格、奖励和规则仍必须由人工查看一手来源后再改数据。仓库内旧的 `competition-monitor.py` 仅作为历史实现保留，不再由 LaunchAgent 调用；它覆盖不足且不满足当前 TLS 安全要求，不应重新启用。

## 官方规则页内容变化监测

内容监测只选择数据中 `sources[].kind === "official"` 的官方／权威证据页。普通行动链接、搜索摘要、聚合站和未明确标为官方的来源不会进入基线。它只执行公开页面的只读 GET，不登录、不提交表单、不绕过机器人防护或访问控制，也不会修改赛事数据。

首次运行建立本机基线：

```bash
npm run radar:watch
```

默认状态文件是：

```text
~/.competition-monitor/competition-source-watch.json
```

状态文件原子替换并使用仅当前用户可读写的权限；只保存规范化正文的 SHA-256、正文长度、成功抓取时间、最终 URL、是否截断、连续失败观察和关联赛事 ID，不保存整页正文。首次运行会报告 `new-baseline`。此后没有变化的 `ok` 不重复列入事件，只报告新增基线、`changed`、失败和恢复。

日常检查可用 JSON 交给维护任务保存：

```bash
npm run radar:watch -- --json
```

先做少量、不会写状态的联网检查：

```bash
npm run radar:watch -- --dry-run --limit 2 --json
```

`--dry-run` 仍会发送只读 GET，只是不创建或更新状态文件。还可以按赛事筛选或改用独立状态文件：

```bash
npm run radar:watch -- --id pazhou-super-claw-2026 --state-file /path/to/review-watch.json
```

可调边界包括 `--timeout-ms`、`--concurrency`、`--max-bytes` 和 `--max-redirects`；它们都有上限。每次重定向都会重新校验协议、端口和 DNS，拒绝内嵌账号、localhost、内网／保留地址与非常规端口；请求使用 Node 默认 TLS 证书校验、有界正文读取和有限并发。截断会在事件与状态中明确标记，因此不能把部分正文哈希误当成完整页面快照。

状态含义：

- `new-baseline`：此前没有成功正文，已建立首个哈希。
- `ok`：正文哈希未变化；只有从失败状态恢复时才作为事件报告。
- `changed`：规范化正文哈希改变，事件同时给出 previous/current hash、最终 URL、长度、截断标志和关联赛事 ID。
- `bot-blocked`：401、403、407、429 或明显机器人验证页；必须用普通浏览器人工复核，不等于赛事失效。
- `uncertain`：超时、5xx、TLS／网络异常、空正文、重定向异常，或首次明确 404/410；不会自动推导赛事状态。
- `dead`：明确 404/410 或 DNS 不存在连续出现至少两次，且首次与确认观察间隔至少 24 小时。即使达到该状态，仍须浏览器人工确认后才能改链接或赛事记录。

`changed` 不会让命令失败；页面不可达也作为复核证据而不是自动纠正依据。只有参数错误、状态文件损坏、TLS 被显式关闭或不安全目标等运行错误使用非零退出码。

### 人工复核变化

对每个 `changed` 事件，按以下顺序处理：

1. 在普通浏览器打开事件中的原始 URL 和最终 URL，确认不是登录页、地区页、同意弹窗或机器人挑战。
2. 对照前后哈希所对应的维护记录，逐项核对报名／提交截止、时区、资格、奖金、费用、IP、开源和线下要求；哈希变化本身不能证明哪个字段改变。
3. 需要改数据时另开人工审核改动，保留官方来源与核验日期，运行数据测试和构建后再部署。内容监测器绝不自动覆盖赛事字段。

“超级龙虾”是必须保留哈希证据的典型：搜索缓存曾显示 7 月 15 日，而 2026-08-02 当前官方原页显示 8 月 5 日。缓存可能来自旧版本或未刷新摘要，当前原页也可能继续更新；因此应以人工访问时的当前官方正文为主要证据，同时保存哈希与冲突历史，不能让缓存自动覆盖 8 月 5 日，也不能让一次页面变化直接改回任一日期。

## JSON 与公开边界

`/competitions.json` 仅公开赛事发现需要的固定字段：

- 身份、名称、组织、分类、等级和适配分；
- 地点、日期标签、兼容截止日期；
- 简介、适用人群、有限数量的奖励与时间轴；
- 详情链接、行动链接和有限数量的来源。

它不输出内部维护备注、抓取日志、隐藏评分依据、环境信息或凭据。新增字段前先判断它是否是用户完成赛事发现和核验所必需的公开信息。

## 部署后抽查

1. 打开 `/competitions/`，验证搜索、筛选和详情选择。
2. 打开一个 `/competitions/<id>/`，核对唯一 H1、canonical、来源和外部行动链接。
3. 请求 `/competitions.json`，确认 Content-Type、记录数和字段边界。
4. 请求 `/llms.txt`，确认没有 HTML 包装。
5. 对本次新增或改动的外部链接用浏览器人工确认。

若页面构建成功但官方规则仍有歧义，保持保守描述并标记待确认，不以部署完成替代事实核验。
